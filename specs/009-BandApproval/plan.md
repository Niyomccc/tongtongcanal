# แผนงาน: ตรวจสอบและอนุมัติวงดนตรี (Band Approval)

## 1. สรุปแนวทาง

1. ผู้จัดงานเข้าดูรายการใบสมัครและเลือกใบสมัครที่ต้องตรวจสอบ
2. ระบบแสดงข้อมูลวง สมาชิก และรายละเอียดการแสดงเพื่อให้ผู้จัดงานประเมินก่อนตัดสินใจ
3. ผู้จัดงานสามารถเลือกอนุมัติ ปฏิเสธ หรือส่งกลับแก้ไข
4. หากเป็นปฏิเสธหรือส่งกลับแก้ไข ระบบต้องมีข้อความที่ไม่ว่างและไม่ใช่ช่องว่างล้วน ก่อนบันทึกผลและเปลี่ยนสถานะ
5. เมื่อบันทึกผลสำเร็จ ระบบอัปเดตสถานะของใบสมัคร และแจ้งให้วงเห็นผ่านหน้าสถานะการสมัครของใบสมัครตนเอง พร้อมข้อความจากผู้จัดงาน
6. ระบบแสดงตัวบอกว่ามีสถานะใหม่ที่ยังไม่ได้เปิดดู และส่งอีเมลแจ้งเป็นทางเลือกเสริม หากอีเมลล้มเหลว ระบบต้องไม่ยกเลิกผลที่บันทึกไว้
7. ระบบเก็บประวัติการอนุมัติทุกเหตุการณ์ของใบสมัคร และจำกัดการมองเห็นประวัติตามบทบาท

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| ภาษา, framework, ฐานข้อมูล และรูปแบบ API | ทีมเลือกเอง ไม่ได้มาจาก spec | ต้องรองรับการแสดงรายการใบสมัคร การตรวจสอบข้อมูลวง การบันทึกผลอนุมัติ/ปฏิเสธ/ส่งกลับแก้ไข การแจ้งผล และการจัดเก็บประวัติ |

## 3. โมเดลข้อมูลเชิงตรรกะ

| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| Application | `application_id`, `band_id`, `event_id`, `submitted_at`, `status`, `decision_message`, `reviewed_by`, `reviewed_at` | FR-APR-01, FR-APR-03, FR-APR-04, FR-APR-05 |
| Band | `band_id`, `user_id`, ข้อมูลวง | FR-APR-02, FR-APR-06 |
| BandMember | `member_id`, `band_id`, ชื่อสมาชิก ตำแหน่ง/เครื่องดนตรี | FR-APR-02 |
| EventApplicationSnapshot | `snapshot_id`, `application_id`, `snapshot_data`, `created_at` | FR-APR-07 |
| ApprovalHistory | `history_id`, `application_id`, `event_id`, `actor_user_id`, `action`, `previous_status`, `new_status`, `message`, `performed_at`, `snapshot_id` | FR-APR-07, NFR-AUD-01 |

หมายเหตุ:
- ค่าคงที่ของสถานะที่ใช้คือ `รอตรวจสอบ`, `ส่งกลับแก้ไข`, `อนุมัติ`, `ปฏิเสธ` ตาม Goal และกฎใน spec
- เมื่อผู้จัดงานส่งกลับให้แก้ไข ระบบต้องระบุข้อความที่ไม่ว่างและไม่ใช่ช่องว่างล้วน ตาม ASM-04
- เมื่อวงส่งใหม่ ใบสมัครเดิมกลับเป็น `รอตรวจสอบ` และไม่สร้างใบสมัครใหม่ ตาม ASM-05
- ประวัติการอนุมัติต้องมีข้อมูลครบตาม FR-APR-07 และเก็บอย่างน้อย 1 ปีตาม ASM-06
- ระบบต้องไม่ให้ผู้ใช้ที่ไม่ใช่ผู้จัดงานที่ได้รับสิทธิ์เข้าถึงหน้ารายการใบสมัครหรือการอนุมัติ ตาม CON-ACC-01 และ NFR-ACC-01

## 4. หน้าจอและการทำงานเชิงตรรกะ

| รายการ | การทำงาน | รองรับ |
|---|---|---|
| รายการใบสมัคร | แสดงใบสมัครทั้งหมดให้ผู้จัดงานเลือกตรวจสอบ | FR-APR-01 |
| หน้าใบสมัคร | แสดงข้อมูลวง สมาชิก และรายละเอียดการแสดง | FR-APR-02 |
| การตัดสินใจ | ให้ผู้จัดงานเลือกอนุมัติ / ปฏิเสธ / ส่งกลับแก้ไข | FR-APR-03 |
| การยืนยันข้อความ | ถ้ากรณีปฏิเสธหรือส่งกลับแก้ไข มีข้อความว่างหรือช่องว่างล้วน ระบบปฏิเสธการบันทึกและไม่เปลี่ยนสถานะ | FR-APR-03, ASM-04 |
| แจ้งผลให้วง | หลังบันทึกผล ระบบอัปเดตหน้าสถานะการสมัครและแสดงสถานะใหม่พร้อมข้อความจากผู้จัดงาน | FR-APR-04, ASM-02 |
| แจ้งใหม่ | ระบบแสดงสัญญาณว่ามีสถานะใหม่ที่ยังไม่ได้เปิดดู | FR-APR-04, AC-APR-04 |
| อีเมลเสริม | ส่งอีเมลแจ้งให้วงทราบเป็นทางเลือกเสริม ไม่ต้องรอให้ email สำเร็จก่อนบันทึกผล | FR-APR-04, ASM-03 |
| ส่งกลับแก้ไข | ระบุสิ่งที่ต้องแก้ไข และให้วงแก้ไขทุกฟิลด์ของข้อมูลเพลง/การแสดงในใบสมัคร | FR-APR-05, ASM-05, ASM-07 |
| ไม่สามารถตรวจสอบ | หากข้อมูลไม่ครบหรือไม่สามารถตรวจสอบได้ แจ้งผู้จัดงานและไม่บันทึกผล | FR-APR-06 |
| ประวัติ | เก็บทุกเหตุการณ์และให้อ่านได้ตามบทบาท | FR-APR-07, NFR-AUD-01 |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| AC-APR-01 | `test_AC_APR_01_view_application_details` | เตรียมใบสมัครที่มีข้อมูลวง สมาชิก และรายละเอียดการแสดง แล้วตรวจว่าผู้จัดงานเห็นครบทุกส่วน |
| AC-APR-02 | `test_AC_APR_02_approve_application` | เลือกอนุมัติจากใบสมัครที่พร้อมใช้งาน แล้วตรวจว่าระบบบันทึกสถานะเป็น "อนุมัติ" |
| AC-APR-03 | `test_AC_APR_03_reject_application_with_reason` | เลือกปฏิเสธพร้อมเหตุผลที่ไม่ว่าง แล้วตรวจว่าระบบบันทึกสถานะเป็น "ปฏิเสธ" และประวัติมีข้อความเหตุผล |
| AC-APR-04 | `test_AC_APR_04_notify_band_new_status` | บันทึกผลการพิจารณาแล้ว ตรวจว่าทางหน้าสถานะการสมัครแสดงสถานะใหม่พร้อมข้อความและสัญญาณว่ามีสถานะใหม่ |
| AC-APR-05 | `test_AC_APR_05_return_for_edit_with_message` | ส่งกลับให้แก้ไขพร้อมข้อความที่ระบุสิ่งที่ต้องแก้ไข แล้วตรวจว่าวงเห็นข้อความและสามารถแก้ไขทุกฟิลด์ของข้อมูลเพลง/การแสดง |
| AC-APR-06 | `test_AC_APR_06_block_invalid_decision` | ใส่ข้อความว่างหรือข้อมูลไม่ครบ แล้วตรวจว่าระบบปฏิเสธการบันทึกและไม่เปลี่ยนสถานะ |
| AC-APR-07 | `test_AC_APR_07_audit_history_created` | ทำการตัดสินใจแล้วตรวจว่ามีประวัติการอนุมัติที่มีข้อมูลครบตาม FR-APR-07 และผู้จัดงานเห็นประวัติได้ ส่วนวงเห็นเฉพาะของตนเอง |
| AC-APR-08 | `test_AC_APR_08_unauthorized_user_denied` | ลองใช้ผู้ใช้ที่ไม่ใช่ผู้จัดงานที่ได้รับสิทธิ์เข้าถึงฟังก์ชันอนุมัติ แล้วตรวจว่าระบบปฏิเสธ |

## 7. ลำดับงาน

1. กำหนดบทบาทและสิทธิ์ผู้จัดงานที่สามารถเข้าถึงรายการใบสมัครและบันทึกผล
2. สร้างหน้าประเมินใบสมัครเพื่อแสดงข้อมูลวง สมาชิก และรายละเอียดการแสดง
3. สร้างฟังก์ชันอนุมัติ/ปฏิเสธ/ส่งกลับแก้ไข พร้อมการตรวจสอบข้อความที่ไม่ว่างและไม่ใช่ช่องว่างล้วน
4. อัปเดตสถานะใบสมัครและบันทึกข้อความจากผู้จัดงานในข้อมูลใบสมัครหลัก
5. เพิ่มการแจ้งผลให้วงผ่านหน้าสถานะการสมัคร และสัญญาณ “มีสถานะใหม่ที่ยังไม่ได้เปิดดู”
6. เพิ่มการส่งอีเมลเป็นช่องทางเสริมที่ไม่รอผล
7. สร้างระบบประวัติการอนุมัติที่เก็บทุกเหตุการณ์ และจำกัดการมองเห็นตามบทบาท
8. ทดสอบตาม AC-APR-01 ถึง AC-APR-08

## 8. สิ่งที่ยังไม่ทำ/ไม่ต้องเดาเพิ่ม

- ไม่เพิ่มสถานะใหม่ที่อยู่นอก 4 ค่า ที่ spec ระบุ
- ไม่กำหนดรูปแบบอีเมลหรือฟิลด์ UI ที่ไม่ระบุใน spec
- ไม่เพิ่มกฎว่าผู้จัดงานต้องแก้ไขข้อมูลบางฟิลด์ด้วยตนเองหรือจำกัดการแก้ไขของวงเกินจาก spec
- ไม่รวม UC-06, UC-08 และ UC-11 ในแผนงานนี้ตาม Out of scope
- ไม่กำหนดเวลาการเก็บข้อมูลเกิน 1 ปีหรือตามระเบียบของมหาวิทยาลัยที่ยังไม่ได้ระบุค่าอย่างชัดเจนใน spec
