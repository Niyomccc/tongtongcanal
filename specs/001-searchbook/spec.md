# Feature: สมัครสมาชิก / เข้าสู่ระบบ (Authentication)
Spec ID: SPEC-AUTH-001 | Source: Use Case Specification UC-01 | Use case: UC-01
Owner: TBD | Status: Draft v2 | Updated: 2569-09-20

## Goal
ผู้ใช้ทุกประเภท (นักศึกษา / ผู้ชม / วงดนตรี / ผู้จัดงาน) สมัครสมาชิกหรือเข้าสู่ระบบ
แล้วเข้าสู่หน้าหลักและใช้งานฟังก์ชันได้ตามสิทธิ์ของบทบาทตนเอง

## Scope
### In scope
- แสดงแบบฟอร์มสมัครสมาชิก / เข้าสู่ระบบ
- ตรวจสอบข้อมูลที่กรอก บันทึกข้อมูลสมาชิกใหม่ / ตรวจสอบบัญชีที่มีอยู่
- นำผู้ใช้เข้าสู่หน้าหลักและกำหนดสิทธิ์ตามบทบาท
### Out of scope
- จัดการบัญชีผู้ใช้โดยผู้ดูแลระบบ (UC-14)

## Constraints
- PRE-AUTH-01 ผู้ใช้ยังไม่ได้เข้าสู่ระบบ (precondition)

## Requirements
- FR-AUTH-01 ระบบต้องแสดงแบบฟอร์มเมื่อผู้ใช้เลือกสมัครสมาชิกหรือเข้าสู่ระบบ        <- UC-01 main flow ขั้น 1-2
- FR-AUTH-02 ระบบต้องตรวจสอบข้อมูลที่ผู้ใช้กรอกตามเงื่อนไขของบทบาทและข้อมูลพื้นฐานที่จำเป็น
  โดยต้องมีเงื่อนไขดังนี้: ทุกช่องบังคับกรอกต้องมีข้อมูล, อีเมลต้องมีรูปแบบที่ถูกต้องและไม่ซ้ำ,
  รหัสผ่านต้องผ่านเงื่อนไขความปลอดภัย, รหัสนักศึกษาต้องตรงรูปแบบของมหาวิทยาลัยและไม่ซ้ำ,
  ชื่อวงต้องไม่ซ้ำ, บทบาทผู้จัดงานและ Admin สมัครเองไม่ได้ และต้องมี Admin ที่มีอยู่แล้วสร้างหรือกำหนดสิทธิ์ผ่าน UC-14
  พร้อมกับแจ้งผู้ใช้เมื่อข้อมูลไม่ถูกต้อง                                              <- UC-01 main flow ขั้น 4
- FR-AUTH-03 เมื่อข้อมูลถูกต้อง ระบบต้องบันทึกข้อมูลสมาชิก (กรณีสมัคร) หรือตรวจสอบบัญชี
  (กรณีเข้าสู่ระบบ) แล้วนำผู้ใช้เข้าสู่หน้าหลักของผู้ใช้                          <- UC-01 main flow ขั้น 5-6
- FR-AUTH-04 เมื่อข้อมูลไม่ถูกต้อง ระบบต้องแจ้งเตือนและให้ผู้ใช้แก้ไขข้อมูล            <- UC-01 alternative flow
- FR-AUTH-05 ระบบต้องกำหนดสิทธิ์การใช้งานตามบทบาทของผู้ใช้แต่ละประเภท โดยผู้จัดงานและ Admin
  ไม่สามารถสมัครเองได้ และบัญชี Admin ต้องสร้างหรือกำหนดสิทธิ์ผ่าน UC-14 เท่านั้น    <- UC-01 acceptance criteria
- FR-AUTH-06 เมื่อฐานข้อมูลใช้งานไม่ได้หรือระบบตรวจสอบบัญชีไม่ได้ ระบบต้องไม่ให้เข้าสู่ระบบ
  และแจ้งผู้ใช้ว่าดำเนินการไม่สำเร็จ                                               <- UC-01 exception flow

## Quality Requirements
- NFR-PERF-01 ระบบตอบสนองภายใน 3 วินาทีที่ p95 และไม่เกิน 3 วินาที เมื่อผู้ใช้พร้อมกัน 50 คน
  นับตั้งแต่ผู้ใช้กดส่งแบบฟอร์มสมัครสมาชิกหรือเข้าสู่ระบบ จนหน้าหลักของผู้ใช้แสดงผล
  ใช้เกณฑ์เดียวกันทั้งกรณีสมัครสมาชิกและเข้าสู่ระบบ                                 <- UC-01 NFR (ประสิทธิภาพ)
- NFR-SEC-01 ระบบต้องรักษาความปลอดภัยของข้อมูลผู้ใช้ โดยยึดมาตรการขั้นต่ำดังนี้: (1) เก็บรหัสผ่านแบบ hash
  พร้อม salt ไม่เก็บ plain text, (2) ใช้ HTTPS TLS 1.2 ขึ้นไปทุกหน้า, (3) session หมดอายุเมื่อไม่ใช้งาน 30 นาที,
  (4) กรอกรหัสผ่านผิดติดกัน 5 ครั้ง ล็อกบัญชีชั่วคราว 15 นาที, (5) ข้อความแจ้งข้อผิดพลาดตอนเข้าสู่ระบบไม่ระบุว่า
  ผิดที่ชื่อผู้ใช้หรือรหัสผ่าน, และ (6) รหัสผ่านต้องยาวอย่างน้อย 8 ตัวอักษร พร้อมเงื่อนไขตามนโยบายของหน่วยงาน
  กรณีปรับเงื่อนไขต้องมีการกำหนดนโยบายชัดเจนและสอดคล้องกับระบบ                    <- UC-01 NFR (ความปลอดภัย)

## Acceptance Criteria
- [ ] AC-AUTH-01 (FR-AUTH-03)
      Given ผู้ใช้ยังไม่มีบัญชี และกรอกข้อมูลสมัครสมาชิกครบถ้วนถูกต้อง
      When  ส่งแบบฟอร์มสมัครสมาชิก
      Then  ระบบบันทึกข้อมูลสำเร็จ และผู้ใช้เข้าสู่หน้าหลักของตนเอง
- [ ] AC-AUTH-02 (FR-AUTH-03)
      Given ผู้ใช้มีบัญชีอยู่แล้ว และกรอกข้อมูลเข้าสู่ระบบถูกต้อง
      When  ส่งแบบฟอร์มเข้าสู่ระบบ
      Then  ผู้ใช้เข้าสู่ระบบได้และเข้าสู่หน้าหลักของตนเอง
- [ ] AC-AUTH-03 (FR-AUTH-04)
      Given ผู้ใช้กรอกข้อมูลไม่ถูกต้อง
      When  ส่งแบบฟอร์ม
      Then  ระบบแจ้งเตือน และให้ผู้ใช้แก้ไขข้อมูลได้
- [ ] AC-AUTH-04 (FR-AUTH-05)
      Given ผู้ใช้แต่ละประเภท (นักศึกษา / ผู้ชม / วงดนตรี / ผู้จัดงาน) เข้าสู่ระบบแล้ว
      When  เข้าใช้ฟังก์ชันต่าง ๆ
      Then  ผู้ใช้ใช้ได้เฉพาะฟังก์ชันตามสิทธิ์ของบทบาทตนเอง
- [ ] AC-AUTH-05 (FR-AUTH-06)
      Given ฐานข้อมูลใช้งานไม่ได้
      When  ผู้ใช้ส่งแบบฟอร์มเข้าสู่ระบบ
      Then  ระบบไม่ให้เข้าสู่ระบบ และแจ้งผู้ใช้ว่าดำเนินการไม่สำเร็จ
- [ ] AC-AUTH-06 (NFR-PERF-01)
      Given ผู้ใช้ส่งแบบฟอร์มสมัครสมาชิกหรือเข้าสู่ระบบ
      When  ระบบประมวลผล
      Then  ระบบตอบสนองภายใน 3 วินาที

## Assumptions & Open Questions
- ASM-01 พฤติกรรมเมื่อเกิด exception (แจ้งผู้ใช้ ไม่บันทึกข้อมูลบางส่วน) เป็นข้อสันนิษฐานของผู้เขียน spec
  เพราะ Use Case ระบุเพียงเงื่อนไขที่เกิดขึ้น
- ASM-02 ฟอร์มสมัครสมาชิกใช้แบบฟอร์มเดียวกันสำหรับทุกบทบาท โดยฟิลด์ร่วมคือ ชื่อ (หรือชื่อวง) อีเมล รหัสผ่าน และยืนยันรหัสผ่าน
  ส่วนฟิลด์เฉพาะบทบาทคือ นักศึกษา: รหัสนักศึกษา / ผู้ชมทั่วไป: เบอร์โทร / วงดนตรี: ชื่อวง ชื่อผู้ติดต่อ และเบอร์โทร
  ข้อมูลรายละเอียดของวง (สมาชิก แนวเพลง เพลงที่แสดง) กรอกภายหลังผ่าน UC-07 และ UC-06
- ASM-03 กฎตรวจสอบข้อมูลสำหรับสมัครสมาชิกมีดังนี้: ทุกช่องบังคับกรอก, อีเมลรูปแบบถูกต้องและไม่ซ้ำ,
  รหัสผ่านตามเงื่อนไขความปลอดภัย, รหัสนักศึกษาตรงรูปแบบของมหาวิทยาลัยและไม่ซ้ำ, ชื่อวงไม่ซ้ำ
- ASM-04 ผู้จัดงานและ Admin สมัครเองไม่ได้ ต้องมี Admin ที่มีอยู่แล้วสร้างหรือกำหนดสิทธิ์ผ่าน UC-14
  บัญชี Admin คนแรกสร้างไว้ตั้งแต่ติดตั้งระบบ
- ASM-05 มาตรการความปลอดภัยขั้นต่ำสำหรับข้อมูลผู้ใช้คือ: (1) เก็บรหัสผ่านแบบ hash พร้อม salt ไม่เก็บ plain text,
  (2) ใช้ HTTPS TLS 1.2 ขึ้นไปทุกหน้า, (3) session หมดอายุเมื่อไม่ใช้งาน 30 นาที, (4) กรอกรหัสผ่านผิดติดกัน 5 ครั้ง
  ล็อกบัญชีชั่วคราว 15 นาที, (5) ข้อความแจ้งข้อผิดพลาดตอนเข้าสู่ระบบไม่ระบุว่าผิดที่ชื่อผู้ใช้หรือรหัสผ่าน,
  และ (6) รหัสผ่านต้องยาวอย่างน้อย 8 ตัวอักษร พร้อมเงื่อนไขตามนโยบายของหน่วยงาน
- ASM-06 มีการวัดประสิทธิภาพแบบ p95 ที่ผู้ใช้พร้อมกัน 50 คน โดยต้องไม่เกิน 3 วินาที ตั้งแต่ผู้ใช้กดส่งแบบฟอร์ม
  จนหน้าหลักของผู้ใช้แสดงผล และใช้เกณฑ์เดียวกันทั้งกรณีสมัครสมาชิกและเข้าสู่ระบบ
- ASM-07 Admin เข้าสู่ระบบผ่านหน้าเข้าสู่ระบบเดียวกับ UC-01 โดยใช้บัญชีที่มีบทบาท Admin แต่ไม่เปิดให้สมัครเป็น Admin เอง
  หลังเข้าสู่ระบบ ระบบนำไปหน้าหลักของ Admin และแสดงเมนู UC-14 / UC-15 ตามสิทธิ์
