# แผนงาน: ตรวจสอบรายชื่อผู้เข้าร่วม (Attendee List)

## 1. สรุปแนวทาง
- ฟีเจอร์นี้ให้ผู้จัดงานเลือกและดูรายชื่อผู้ลงทะเบียนของอีเว้นต์ที่ตนเป็นเจ้าของ/รับผิดชอบเท่านั้น โดยตรวจสิทธิ์จากความสัมพันธ์ระหว่างผู้ใช้กับอีเว้นต์ ไม่ใช่จาก role เพียงอย่างเดียว (FR-ATT-01, FR-ATT-06, NFR-ACC-01, CON-ACC-01)
- รายชื่อจะแสดงข้อมูลขั้นต่ำ ได้แก่ ชื่อ-นามสกุล, สถานะการลงทะเบียน และวันที่ลงทะเบียน ส่วนอีเมลและเบอร์โทรจะแสดงได้เมื่อจำเป็นต่อการปฏิบัติงานจริง และต้องบันทึก access log ทุกครั้งที่เข้าถึง (FR-ATT-02, NFR-SEC-01)
- จำนวนผู้ลงทะเบียนจะนับเฉพาะรายการที่มีสถานะยืนยันสำเร็จ (CONFIRMED) ไม่รวมรายการที่ยกเลิก ถูกลบ หรือไม่สำเร็จ (FR-ATT-03, NFR-DAT-01)
- ระบบต้องรองรับการค้นหา/กรองรายชื่อ และแจ้งผู้จัดงานเมื่อไม่พบข้อมูล (FR-ATT-04, FR-ATT-05)
- เทคโนโลยีที่ใช้ในแผนนี้เป็นการเลือกของทีม ไม่ได้มาจาก spec เพราะ spec ยังไม่ระบุภาษา ฐานข้อมูล หรือ framework

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| Web application frontend | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สำหรับหน้าเลือกอีเว้นต์ รายชื่อ การค้นหา/กรอง และข้อความแจ้งผล |
| Backend API | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้ตรวจสิทธิ์ ดึงข้อมูล คำนวณจำนวน และควบคุมการเข้าถึง PII |
| Relational database หรือฐานข้อมูลที่ทีมเลือก | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้เก็บข้อมูลอีเว้นต์ การลงทะเบียน และ access log |
| Access-control middleware/service | FR-ATT-01, FR-ATT-06, NFR-ACC-01, CON-ACC-01 | ตรวจความสัมพันธ์ระหว่างผู้ใช้กับอีเว้นต์ก่อนคืนข้อมูล |
| Access-log mechanism | FR-ATT-02, NFR-SEC-01 | บันทึกทุกครั้งที่มีการเข้าถึงอีเมลหรือเบอร์โทร |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ FR / NFR |
|---|---|---|
| Event | id, owner_or_responsible_user_id หรือความสัมพันธ์ผู้รับผิดชอบ | FR-ATT-01, FR-ATT-06, CON-ACC-01 |
| Registration | id, event_id, user_id, full_name, registration_status, registered_at, email, phone, deleted_at | FR-ATT-02, FR-ATT-03, FR-ATT-05, NFR-DAT-01 |
| AccessLog | id, actor_user_id, event_id, registration_id หรือข้อมูลที่เข้าถึง, data_type, action, result, accessed_at | FR-ATT-02, FR-ATT-06, NFR-SEC-01 |

หมายเหตุ:
- ฟิลด์ชื่อจริงของความสัมพันธ์ผู้รับผิดชอบอีเว้นต์และสถานะการลงทะเบียนให้ใช้ตาม schema ของระบบหลัก ทีมต้องเลือกชื่อเทคนิคเองโดยไม่เปลี่ยนความหมายใน spec
- การ query จำนวนต้องกรอง `registration_status = CONFIRMED` และไม่นับรายการที่ยกเลิก ถูกลบ หรือไม่สำเร็จ
- การตอบกลับรายชื่อปกติให้ส่งเฉพาะชื่อ-นามสกุล, สถานะการลงทะเบียน และวันที่ลงทะเบียน ส่วน email/phone ต้องผ่านการตรวจความจำเป็นและสิทธิ์เพิ่มเติม

## 4. หน้าที่สำคัญ / API / UI

### 4.1 หน้าและ workflow
- หน้าเลือกอีเว้นต์ที่ผู้ใช้เป็นเจ้าของ/รับผิดชอบเท่านั้น (FR-ATT-01, FR-ATT-06)
- หน้ารายชื่อผู้ลงทะเบียน แสดงข้อมูลขั้นต่ำและจำนวนผู้ยืนยันสำเร็จ (FR-ATT-02, FR-ATT-03)
- ช่องค้นหา/ตัวกรองรายชื่อ (FR-ATT-04)
- ข้อความไม่พบข้อมูลเมื่อผลลัพธ์ไม่มีรายการ (FR-ATT-05)
- การเปิดดูอีเมล/เบอร์โทรต้องผ่านการตรวจสิทธิ์และเหตุผลความจำเป็นตามนโยบายที่ทีมกำหนด พร้อมบันทึก access log (FR-ATT-02, NFR-SEC-01)

### 4.2 API ที่ต้องมี
- GET endpoint สำหรับคืนรายการอีเว้นต์ที่ผู้ใช้เป็นเจ้าของ/รับผิดชอบ (FR-ATT-01)
- GET endpoint สำหรับคืนรายชื่อของอีเว้นต์ที่เลือก พร้อมข้อมูลขั้นต่ำและจำนวน `CONFIRMED` (FR-ATT-02, FR-ATT-03, NFR-DAT-01)
- Query parameters หรือ request fields สำหรับค้นหา/กรองรายชื่อ (FR-ATT-04)
- Endpoint หรือ service สำหรับขอข้อมูล PII แบบจำกัดสิทธิ์ และบันทึกผลการเข้าถึงทุกครั้ง (FR-ATT-02, NFR-SEC-01)

หมายเหตุ: ชื่อ route, HTTP method, รูปแบบ response และเทคโนโลยีเป็นสิ่งที่ทีมเลือกเอง ไม่ได้มาจาก spec

### 4.3 กฎการประมวลผล
1. ตรวจสอบว่าผู้ใช้มีความสัมพันธ์เป็นเจ้าของ/ผู้รับผิดชอบกับอีเว้นต์ที่ร้องขอ
2. หากไม่มีสิทธิ์ ให้ปฏิเสธคำขอและไม่คืนข้อมูลผู้ลงทะเบียน (FR-ATT-06, NFR-ACC-01)
3. ดึงข้อมูลการลงทะเบียนของอีเว้นต์นั้น และคำนวณจำนวนจากสถานะ `CONFIRMED` เท่านั้น (FR-ATT-03, NFR-DAT-01)
4. คืนเฉพาะฟิลด์ขั้นต่ำในรายการปกติ (FR-ATT-02, NFR-SEC-01)
5. หากมีการเข้าถึงอีเมลหรือเบอร์โทร ให้ตรวจสิทธิ์/ความจำเป็นและเขียน access log ทั้งกรณีสำเร็จและถูกปฏิเสธ (FR-ATT-02, NFR-SEC-01)
6. หากไม่มีผลลัพธ์ ให้ส่งสถานะ/ข้อความที่ทำให้ UI แจ้งว่าไม่พบข้อมูล (FR-ATT-05)

## 5. ตารางตรวจ Constraints และ Assumptions

| Constraint / Assumption ID | ถูกนำไปใช้ในแผน | สถานะ |
|---|---|---|
| PRE-ATT-01 | ตรวจว่ามีข้อมูลการลงทะเบียนก่อนแสดงรายชื่อและจำนวน | ใช้แล้ว |
| CON-ACC-01 | ใช้ร่วมกับ access-control ก่อนคืนข้อมูลทุก endpoint | ใช้แล้ว |
| ASM-01 | กำหนด empty-result handling ให้แจ้งว่าไม่พบข้อมูล | ใช้แล้ว |
| ASM-02 | ใช้ filter สถานะ `CONFIRMED` ใน query count | ใช้แล้ว |
| ASM-03 | ใช้ event ownership/responsibility relation ใน authorization | ใช้แล้ว |
| ASM-04 | ใช้กำหนด response fields และ access-log behavior ของ PII | ใช้แล้ว |

| AC-ATT-05 | test_AC_ATT_05_no_attendees_message | ใช้อีเว้นต์ที่ไม่มีข้อมูลผู้ลงทะเบียน ตรวจว่าระบบแจ้งว่าไม่พบข้อมูลผู้ลงทะเบียน |

## 7. ลำดับงาน

1. ยืนยัน schema ที่มีอยู่ของ Event, Registration, สถานะการลงทะเบียน และความสัมพันธ์เจ้าของ/ผู้รับผิดชอบ โดยไม่เพิ่มความหมายใหม่นอก spec
2. สร้าง access-control service ที่ตรวจความสัมพันธ์ผู้ใช้กับอีเว้นต์ก่อนอ่านข้อมูล (FR-ATT-01, FR-ATT-06, NFR-ACC-01, CON-ACC-01)
3. สร้าง query รายชื่อที่คืนเฉพาะข้อมูลขั้นต่ำ และ query count ที่กรอง `CONFIRMED` (FR-ATT-02, FR-ATT-03, NFR-DAT-01)
4. สร้างหน้าเลือกอีเว้นต์และหน้ารายชื่อ พร้อมค้นหา/กรองและ empty state (FR-ATT-01, FR-ATT-04, FR-ATT-05)
5. เพิ่มการเข้าถึงอีเมล/เบอร์โทรแบบจำกัดสิทธิ์และบันทึก access log ทุกครั้ง (FR-ATT-02, NFR-SEC-01)
6. เชื่อม error handling สำหรับผู้ไม่มีสิทธิ์และกรณีไม่พบข้อมูล โดยไม่เปิดเผยข้อมูลผู้ลงทะเบียน (FR-ATT-05, FR-ATT-06)
7. ทดสอบทุก AC และตรวจ traceability ก่อนส่งให้ทีมตรวจ

## 8. สิ่งที่ยังไม่ทำ / Open Questions

- spec ไม่มี Open Questions ค้างอยู่หลังการ clarify
- ชื่อ route, schema เชิงเทคนิค, framework, ฐานข้อมูล, รูปแบบ access log และวิธีขอ PII เป็นรายละเอียดที่ทีมต้องเลือกเอง ไม่ใช่การตัดสินใจจาก spec
- แผนนี้ไม่รวมการลงทะเบียนเข้าชมงานหรือการยกเลิกการลงทะเบียนตาม Out of scope ของ spec

## 9. ตัวชี้วัดความสำเร็จ

- ผู้จัดงานเห็นรายชื่อได้เฉพาะอีเว้นต์ที่ตนเป็นเจ้าของ/รับผิดชอบ
- รายการปกติแสดงเฉพาะชื่อ-นามสกุล, สถานะการลงทะเบียน และวันที่ลงทะเบียน
- จำนวนผู้ลงทะเบียนถูกต้องและนับเฉพาะสถานะ `CONFIRMED`
- การค้นหา/กรองและข้อความไม่พบข้อมูลทำงานตาม AC
- ผู้ไม่มีสิทธิ์ไม่สามารถดูรายชื่อหรือ PII ได้ และทุกการเข้าถึง PII มี access log
