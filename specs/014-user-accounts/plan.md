# แผนงาน: จัดการบัญชีผู้ใช้ (User Account Management)

## 1. สรุปแนวทาง
- ฟีเจอร์นี้ให้ผู้ดูแลระบบที่ผ่าน authentication flow เดียวกับ UC-01 จัดการบัญชีผู้ใช้ผ่านรายการบัญชี โดยการสร้าง/กำหนดบัญชี Admin ต้องเป็นไปตาม UC-14 และ Admin คนแรกต้องมีอยู่ตั้งแต่ติดตั้งระบบ (PRE-ACC-01, ASM-02)
- ระบบต้องรองรับการเพิ่ม แก้ไข ระงับ และยกเลิกการระงับบัญชี โดยการระงับต้อง force logout/invalidate session ของผู้ใช้ทันที (FR-ACC-02, ASM-03)
- ทุก action ที่แก้ไขบัญชีหรือสิทธิ์ต้องตรวจสอบสิทธิ์ Admin ฝั่งระบบ และทุกการเปลี่ยนแปลงต้องมี immutable audit log ที่เก็บข้อมูลก่อนและหลังการเปลี่ยนแปลง (NFR-SEC-01, NFR-ACC-01, ASM-04)
- แผนนี้ไม่ตัดสินใจแทนทีมในเรื่องฟิลด์/validation, ชุดสิทธิ์, การลบบัญชี และขอบเขตการป้องกัน UI/URL/API เพราะยังเป็น Open Questions ใน spec

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| Web application frontend | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สำหรับรายการบัญชี ฟอร์มแก้ไข และข้อความแจ้งผล |
| Backend API/service | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้ตรวจสิทธิ์ ตรวจข้อมูล บันทึกบัญชี และจัดการ session |
| User account storage | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้เก็บบัญชี สถานะ และสิทธิ์ของผู้ใช้ |
| Session invalidation mechanism | FR-ACC-02, ASM-03 | ต้องทำให้ session ของบัญชีที่ถูกระงับใช้ต่อไม่ได้ทันที |
| Immutable audit-log mechanism | NFR-SEC-01, ASM-04 | วิธีทำให้แก้ไข/ลบไม่ได้ให้ทีมเลือก โดยต้องรักษาข้อมูลที่ spec บังคับ |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ FR / NFR |
|---|---|---|
| UserAccount | id, account fields ตาม schema ระบบ, account_status | FR-ACC-01, FR-ACC-02, FR-ACC-03 |
| UserRoleAssignment | user_id, role/permission fields ตาม schema ระบบ | FR-ACC-04, NFR-ACC-01 |
| SessionState | session_id, user_id, status หรือ invalidated_at | FR-ACC-02, ASM-03 |
| AccountAuditLog | actor, action, target_user, timestamp, old_value, new_value | NFR-SEC-01, ASM-04 |

หมายเหตุ:
- ชื่อฟิลด์บัญชีและค่าชุดสิทธิ์ยังไม่กำหนดใน spec จึงต้องรอคำตอบ Q-03 และ Q-04
- กลไก immutable ของ AccountAuditLog ยังไม่ถูกเลือกใน spec และห้ามสรุปแทนทีม
- ข้อมูลสำหรับ Admin คนแรกเป็นส่วนหนึ่งของการติดตั้งระบบตาม PRE-ACC-01 และ ASM-02 แต่รายละเอียดวิธี seed ยังไม่กำหนด

## 4. หน้าที่สำคัญ / workflow

### 4.1 หน้าจอและ workflow
- หน้าแสดงรายการบัญชีและเลือกบัญชี (FR-ACC-01; รายละเอียดฟิลด์/ค้นหา/เรียงลำดับรอ Q-06)
- ฟอร์มเพิ่มหรือแก้ไขบัญชี พร้อม validation ตามข้อสรุปที่จะได้จาก Q-03 (FR-ACC-02, FR-ACC-03)
- การระงับและยกเลิกการระงับบัญชี โดยแสดงผลการดำเนินการและทำให้ session เดิมของบัญชีที่ถูกระงับใช้ต่อไม่ได้ทันที (FR-ACC-02, ASM-03)
- ฟอร์มเปลี่ยนสิทธิ์ผู้ใช้ โดยใช้เฉพาะชุดสิทธิ์ที่ทีมยืนยันหลังตอบ Q-04 (FR-ACC-04)
- ปุ่มยกเลิกก่อนบันทึกต้องคืนข้อมูลในหน้าจอโดยไม่เปลี่ยนข้อมูลบัญชีที่บันทึกแล้ว (FR-ACC-05)
- ข้อความแจ้งกรณีไม่พบผู้ใช้หรือข้อมูลไม่ถูกต้องโดยไม่บันทึกข้อมูล (FR-ACC-06)

### 4.2 การตรวจสิทธิ์
1. ตรวจว่า actor มีสิทธิ์ Admin ก่อนทุก action ที่เพิ่ม แก้ไข ระงับ ปลดระงับ หรือเปลี่ยนสิทธิ์ (NFR-SEC-01, NFR-ACC-01)
2. ตรวจสิทธิ์ฝั่งระบบทุกครั้ง ไม่พึ่งการซ่อนเมนูเพียงอย่างเดียว
3. ขอบเขตการป้องกัน URL/API ต้องดำเนินการตามคำตอบ Q-05 และห้ามเดาในแผนนี้
4. ผู้ไม่มีสิทธิ์ต้องไม่ได้รับข้อมูลหรือผลการดำเนินการของเมนูจัดการบัญชี (FR-ACC-07, AC-ACC-05)

### 4.3 การบันทึกและ force logout
1. ก่อนบันทึกการเปลี่ยนแปลง ให้ตรวจข้อมูลตาม validation ที่ทีมกำหนด (FR-ACC-03)
2. เมื่อระงับบัญชี ให้เปลี่ยนสถานะบัญชีและ invalidate session ที่ใช้งานอยู่ของ target user ทันที (FR-ACC-02, ASM-03)
3. เมื่อยกเลิกการระงับ ให้คืนสิทธิ์การใช้งานบัญชีตามกฎที่ทีมกำหนด โดยไม่สร้าง session เดิมกลับมาเอง (FR-ACC-02, ASM-03)
4. เมื่อเปลี่ยนบัญชีหรือสิทธิ์สำเร็จ ให้บันทึก actor, action, target user, timestamp, old value และ new value ใน audit log ที่แก้ไข/ลบไม่ได้ (NFR-SEC-01, ASM-04)
5. หาก validation หรือการค้นหา target user ไม่ผ่าน ให้ไม่บันทึกการเปลี่ยนแปลงบัญชี (FR-ACC-06)

## 5. ตารางตรวจ Constraints และ Assumptions

| Constraint / Assumption ID | ถูกนำไปใช้ในแผน | สถานะ |
|---|---|---|
| PRE-ACC-01 | ใช้ authentication flow เดียวกับ UC-01 และเตรียม Admin คนแรกตั้งแต่ติดตั้ง | ใช้แล้ว |
| ASM-01 | ใช้ error handling ที่แจ้งผู้ดูแลระบบและไม่บันทึกเมื่อเกิด exception | ใช้แล้ว |
| ASM-02 | ใช้กำหนด login flow, ห้ามสมัคร Admin ผ่านหน้าสมัคร และรองรับ Admin คนแรกที่ seed | ใช้แล้ว |
| ASM-03 | ใช้สถานะระงับ/ปลดระงับและ session invalidation ทันที | ใช้แล้ว |
| ASM-04 | ใช้ authorization check และ immutable audit log สำหรับทุกการเปลี่ยนแปลง | ใช้แล้ว |
| Q-02 ถึง Q-06 | ไม่กำหนดพฤติกรรมแทนทีม; ต้องปิดคำถามก่อนรายละเอียด implementation | รอคำตอบ |

| AC ID | ชื่อ test | วิธีทดสอบ |
|---|---|---|
| AC-ACC-01 | test_AC_ACC_01_account_update_and_suspend | ใช้ Admin เพิ่ม/แก้ไขบัญชีและระงับบัญชี ตรวจว่าบันทึกสำเร็จ เมื่อระงับให้ตรวจว่า session ที่ใช้งานอยู่ถูก invalidate ทันที; การยกเลิกระงับตาม FR-ACC-02 ต้องทดสอบร่วมด้วย แต่ยังไม่มี AC แยกใน spec |
| AC-ACC-02 | test_AC_ACC_02_permission_change_and_audit_log | ใช้ Admin เปลี่ยนสิทธิ์ ตรวจว่าผู้ใช้ได้รับสิทธิ์ใหม่ และ audit log มี actor, action, target user, timestamp, old value, new value และแก้ไข/ลบไม่ได้ |
| AC-ACC-03 | test_AC_ACC_03_cancel_before_save | เริ่มแก้ไขบัญชีแล้วกดยกเลิกก่อนบันทึก ตรวจว่าข้อมูลที่บันทึกไว้ไม่เปลี่ยน |
| AC-ACC-04 | test_AC_ACC_04_invalid_or_missing_account_blocked | ทดสอบ target user ที่ไม่พบและข้อมูลไม่ถูกต้อง ตรวจว่าระบบแจ้งผลและไม่บันทึก |
| AC-ACC-05 | test_AC_ACC_05_non_admin_blocked | ใช้ผู้ไม่มีสิทธิ์ Admin พยายามเข้าเมนูจัดการบัญชี ตรวจว่าระบบปฏิเสธตามขอบเขตที่ทีมยืนยันใน Q-05 |

## 7. ลำดับงาน

1. ยืนยัน schema บัญชี สถานะ และความสัมพันธ์สิทธิ์ที่ระบบหลักใช้อยู่ โดยไม่กำหนดค่าที่ยังเป็น Q-02 ถึง Q-06
2. เชื่อม authentication flow เดียวกับ UC-01 และเตรียม Admin คนแรกตาม PRE-ACC-01/ASM-02
3. สร้าง authorization check ฝั่งระบบสำหรับทุก action ที่แก้ไขบัญชีหรือสิทธิ์ (NFR-SEC-01, NFR-ACC-01)
4. สร้างรายการบัญชีและ workflow เพิ่ม/แก้ไข/ระงับ/ปลดระงับตาม FR-ACC-01 ถึง FR-ACC-03 หลังได้คำตอบเรื่องฟิลด์และ validation
5. สร้าง session invalidation ที่ทำงานทันทีเมื่อระงับบัญชี (FR-ACC-02, ASM-03)
6. สร้างการเปลี่ยนสิทธิ์และ immutable audit log ตาม FR-ACC-04 และ NFR-SEC-01
7. เพิ่ม cancel-before-save และ error handling ตาม FR-ACC-05 และ FR-ACC-06
8. ทดสอบ AC-ACC-01 ถึง AC-ACC-05 และตรวจ traceability ก่อนส่งให้ทีมตรวจ

## 8. สิ่งที่ยังไม่ทำ / Open Questions

- Q-02 ยังไม่ระบุว่าการลบบัญชีอยู่ในขอบเขตหรือไม่
- Q-03 ยังไม่ระบุฟิลด์บังคับและ validation ของแต่ละ action
- Q-04 ยังไม่ระบุชุดสิทธิ์ที่เปลี่ยนได้และข้อจำกัดการเปลี่ยนสิทธิ์ของ Admin
- Q-05 ยังไม่ระบุว่าการป้องกันผู้ไม่มีสิทธิ์ต้องครอบคลุม URL/API หรือเฉพาะเมนู
- Q-06 ยังไม่ระบุฟิลด์รายการบัญชีและเงื่อนไขค้นหา/เรียงลำดับ
- FR-ACC-01 ยังถูก trace ไป AC-ACC-01 แม้ AC-ACC-01 ไม่กล่าวถึงการแสดงรายการโดยตรง จึงต้องตรวจทานกับทีมก่อน implementation
- FR-ACC-02 มีพฤติกรรมปลดระงับเพิ่มขึ้น แต่ยังไม่มี AC แยกสำหรับปลดระงับ จึงต้องตรวจทานกับทีมโดยไม่สร้าง ID ใหม่ในแผนนี้

## 9. ตัวชี้วัดความสำเร็จ

- Admin ใช้ authentication flow เดียวกับ UC-01 และ Admin คนแรกถูกเตรียมไว้ตามข้อกำหนด
- ผู้ไม่มีสิทธิ์ไม่สามารถเข้าถึงการจัดการบัญชีผ่านการตรวจสิทธิ์ฝั่งระบบ
- การระงับบัญชีทำให้ session เดิมของผู้ใช้ถูก invalidate ทันที และการปลดระงับคืนสิทธิ์ได้
- ทุกการเปลี่ยนบัญชีหรือสิทธิ์มี immutable audit log ครบ actor, action, target user, timestamp, old value และ new value
- ทุก AC ที่มีอยู่ใน spec มี test case และประเด็นที่ยังไม่มี AC ถูกระบุไว้เป็นข้อค้างตรวจทาน
