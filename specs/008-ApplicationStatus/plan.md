# แผนงาน: ตรวจสอบสถานะการสมัคร (Application Status)

## 1. สรุปแนวทาง

1. วงที่เข้าสู่ระบบเลือกเมนูสถานะการสมัครเพื่อดูรายการใบสมัครทั้งหมดของตนเอง
2. ระบบดึงใบสมัครที่เกี่ยวข้องกับวงนั้นแล้วเรียงตามสถานะตามลำดับ: ส่งกลับแก้ไข > รอตรวจสอบ > อนุมัติ > ปฏิเสธ
3. ภายในสถานะเดียวกัน ระบบเรียงตามวันที่ส่งล่าสุดก่อน
4. แต่ละรายการแสดงชื่ออีเว้นต์ สถานะ วันที่ส่ง และข้อความจากผู้จัดงาน (ถ้ามี)
5. หากกดเข้าไปที่รายการใด ระบบเปิดดูรายละเอียดใบสมัครนั้นได้
6. หากวงไม่มีใบสมัครเลย ระบบแสดงข้อความว่าไม่พบใบสมัคร
7. หากมีใบสมัครของวงอื่นในระบบ ระบบกรองให้เห็นเฉพาะใบสมัครของวงที่ล็อกอินเท่านั้น

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| ภาษา, framework, ฐานข้อมูล และรูปแบบ API | ทีมเลือกเอง ไม่ได้มาจาก spec | ต้องรองรับการแสดงรายการใบสมัคร การกรองตามวงที่ล็อกอิน การเรียงลำดับตามสถานะ และการแสดงข้อความจากผู้จัดงาน |

## 3. โมเดลข้อมูลเชิงตรรกะ

| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| Band | `band_id`, `user_id`, ชื่อวง | FR-STS-05, NFR-ACC-01 |
| Event | `event_id`, ชื่ออีเว้นต์ | FR-STS-01, FR-STS-02 |
| Application | `application_id`, `band_id`, `event_id`, `submitted_at`, `status`, `review_message` | FR-STS-01, FR-STS-02, FR-STS-03, NFR-DAT-01 |
| ApplicationHistory | `application_id`, `status`, `message`, `updated_at`, `updated_by` | ASM-03, ASM-05 |

หมายเหตุ:
- ค่าคงที่ของสถานะที่ใช้คือ `รอตรวจสอบ`, `ส่งกลับแก้ไข`, `อนุมัติ`, `ปฏิเสธ` ตาม Goal และ ASM-04
- การส่งกลับแก้ไขและการปฏิเสธใช้ช่องเดียวกันคือ `review_message` แต่มีความหมายต่างกันตามสถานะของใบสมัคร ตาม ASM-03
- เมื่อมีการส่งกลับให้แก้ไขแล้ววงแก้ไขใหม่ ระบบต้องอัปเดตใบสมัครเดิมกลับเป็นสถานะ `รอตรวจสอบ` โดยไม่สร้างใบสมัครใหม่ ตาม ASM-04
- หากปฏิเสธ ต้องมีข้อความจากผู้จัดงานที่ไม่เป็นค่าว่างและบันทึกในประวัติการอนุมัติของใบสมัครเดียวกัน ตาม ASM-03 และ ASM-05

## 4. หน้าจอและการทำงานเชิงตรรกะ

| รายการ | การทำงาน | รองรับ |
|---|---|---|
| เมนูสถานะการสมัคร | เปิดหน้าแสดงรายการใบสมัครของวงที่ล็อกอิน | FR-STS-01 |
| รายการใบสมัคร | ดึงใบสมัครทั้งหมดของวงที่ล็อกอินและเรียงตามสถานะ วันที่ส่ง ล่าสุดก่อน | FR-STS-01, ASM-02 |
| การกรองข้อมูล | แสดงเฉพาะใบสมัครที่เป็นของวงปัจจุบัน ไม่แสดงของวงอื่น | FR-STS-05, NFR-ACC-01, AC-STS-05 |
| รายการแต่ละใบสมัคร | แสดงชื่ออีเว้นต์ สถานะ วันที่ส่ง และข้อความจากผู้จัดงาน (ถ้ามี) | FR-STS-02 |
| รายละเอียดใบสมัคร | เมื่อกดเข้ารายการ ให้แสดงรายละเอียดของใบสมัครนั้นได้ | FR-STS-05 |
| สถานะระหว่างพิจารณา | แสดงสถานะตามสถานะจริง เช่น รอตรวจสอบ หรือ ส่งกลับแก้ไข | FR-STS-03, AC-STS-03 |
| ไม่พบใบสมัคร | แสดงข้อความว่าไม่พบใบสมัคร | FR-STS-04, AC-STS-04 |
| ปฏิเสธ | แสดงสถานะปฏิเสธและข้อความเหตุผลจากผู้จัดงาน | FR-STS-02, AC-STS-02 |

## 5. ตารางตรวจ Constraints และ Assumptions

| ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| PRE-STS-01 | กำหนดว่าระบบจะทำงานเฉพาะเมื่อวงเคยส่งใบสมัครเข้าร่วมงานแล้ว | ใช้แล้ว |
| ASM-02 | กำหนดลำดับและการเรียงรายการใบสมัครตามสถานะและวันที่ส่ง | ใช้แล้ว |
| ASM-03 | กำหนดการใช้ช่องข้อความเดียวกันระหว่างส่งกลับแก้ไขและปฏิเสธ และข้อบังคับว่าคำอธิบายเมื่อปฏิเสธต้องไม่ว่าง | ใช้แล้ว |
| ASM-04 | กำหนดว่าใบสมัครที่ส่งกลับแก้ไขยังเป็นใบสมัครเดิม และไม่สร้างใบสมัครใหม่เมื่อแก้ไขส่งใหม่ | ใช้แล้ว |
| ASM-05 | กำหนดว่าการปฏิเสธต้องบันทึกเหตุผลไว้ในประวัติการอนุมัติ | ใช้แล้ว |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| AC-STS-01 | `test_AC_STS_01_show_approved_status` | เตรียมใบสมัครที่สถานะเป็นอนุมัติ แล้วตรวจว่าหน้าสถานะการสมัครแสดงสถานะ "อนุมัติ" |
| AC-STS-02 | `test_AC_STS_02_show_rejected_status_and_reason` | เตรียมใบสมัครที่สถานะเป็นปฏิเสธ พร้อมข้อความเหตุผลจากผู้จัดงาน แล้วตรวจว่าระบบแสดงสถานะ "ปฏิเสธ" และข้อความเหตุผลที่ไม่ว่าง |
| AC-STS-03 | `test_AC_STS_03_show_pending_or_returned_status` | เตรียมใบสมัครที่สถานะเป็นรอตรวจสอบหรือส่งกลับแก้ไข แล้วตรวจว่าระบบแสดงสถานะที่ตรงกับปัจจุบันและข้อความจากผู้จัดงาน (ถ้ามี) |
| AC-STS-04 | `test_AC_STS_04_no_application_message` | เตรียมสถานการณ์ที่วงไม่มีใบสมัครเลย แล้วตรวจว่าระบบแสดงข้อความ "ไม่พบใบสมัคร" |
| AC-STS-05 | `test_AC_STS_05_show_only_own_applications_in_order` | เตรียมใบสมัครของวงอื่นและของวงที่ล็อกอินพร้อมกัน แล้วตรวจว่าระบบแสดงเฉพาะของวงที่ล็อกอิน และเรียงตามลำดับที่กำหนด |

## 7. ลำดับงาน

1. กำหนดโครงสร้างข้อมูลใบสมัครและสถานะให้สอดคล้องกับ 4 ค่า: รอตรวจสอบ / ส่งกลับแก้ไข / อนุมัติ / ปฏิเสธ
2. จัดทำ API หรือฟังก์ชันดึงใบสมัครของวงที่ล็อกอิน โดยกรองตาม `band_id` หรือข้อมูลเจ้าของใบสมัครที่เท่ากับผู้ใช้ปัจจุบัน
3. จัดทำการเรียงข้อมูลตามสถานะ และภายในสถานะเดียวกันเรียงตามวันที่ส่งล่าสุดก่อน
4. สร้างหน้ารายการสถานะการสมัครเพื่อแสดงชื่ออีเว้นต์ สถานะ วันที่ส่ง และข้อความจากผู้จัดงาน
5. เพิ่มการเปิดดูรายละเอียดใบสมัครจากรายการที่เลือก
6. จัดการกรณีไม่พบใบสมัครและกรณีมีใบสมัครของวงอื่นในระบบให้แสดงเฉพาะข้อมูลของตนเอง
7. ทำการทดสอบตาม AC-STS-01 ถึง AC-STS-05

## 8. สิ่งที่ยังไม่ทำ/ไม่ต้องเดาเพิ่ม

- ไม่เพิ่มสถานะใหม่หรือข้อความเพิ่มเติมนอกเหนือจากที่ spec ระบุ
- ไม่เพิ่มกฎการเรียงแบบอื่นที่ไม่ได้ระบุใน ASM-02
- ไม่กำหนดแก้ไขเพิ่มเติมเรื่องเหตุผลปฏิเสธหรือข้อความส่งกลับนอกเหนือจากข้อมูลที่ทีมตอบชัดแล้ว
- ไม่รวม UC-06 และ UC-09 ในแผนงานนี้ตาม Out of scope
