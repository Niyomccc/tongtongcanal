## 1. สรุปแนวทาง

1. วงดนตรีที่เข้าสู่ระบบแล้วเลือกอีเว้นต์ที่เปิดรับสมัครและกรอกข้อมูลเพลง/การแสดง
2. ระบบแสดงข้อมูลวงจาก UC-07 แบบแก้ไขไม่ได้ และตรวจสอบว่าข้อมูลบังคับครบถ้วน
3. ระบบตรวจสอบความยาวการแสดงรวมและจำนวนเพลงเทียบกับข้อจำกัดของอีเว้นต์
4. เมื่อส่งสำเร็จ ระบบเก็บสำเนาข้อมูลวงและข้อมูลเพลง/การแสดงไว้กับใบสมัคร
5. ใบสมัครที่บันทึกสำเร็จมีสถานะ "รอตรวจสอบ" และแสดงสถานะนี้แก่ผู้ใช้

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React (Vite) | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สร้างหน้าจอเลือกอีเว้นต์และแบบฟอร์มสมัคร |
| Python FastAPI | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้รับคำขอ ตรวจสอบข้อมูล และบันทึกใบสมัคร |
| ฐานข้อมูลเชิงสัมพันธ์ | ทีมเลือกเอง ไม่ได้มาจาก spec | ต้องรองรับการเก็บสำเนาข้อมูลวงและสถานะใบสมัคร |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| Event | `event_id`, `name`, `application_status`, ข้อจำกัดเวลาแสดงและจำนวนเพลง | FR-APP-01, FR-APP-03, AC-APP-01, AC-APP-04 |
| BandProfileReference | `band_id`, ข้อมูลวงจาก UC-07, สถานะความครบถ้วนของฟิลด์บังคับ | FR-APP-02, FR-APP-05, ASM-02 |
| BandApplication | `application_id`, `event_id`, `band_id`, สำเนาข้อมูลวง, ข้อมูลเพลง/การแสดง, `status` | FR-APP-02, FR-APP-04, NFR-SEC-01, AC-APP-02, AC-APP-03 |
| PerformanceSong | `song_name`, ประเภทเพลง, ศิลปินเดิมเมื่อเป็นเพลงคัฟเวอร์ | FR-APP-02, FR-APP-03 |
| ApplicationStatus | `รอตรวจสอบ`, `อนุมัติ`, `ปฏิเสธ` | FR-APP-04, ASM-06 |

หมายเหตุ: `BandApplication` ต้องเก็บ snapshot ของข้อมูลวง ณ เวลาส่งใบสมัครแยกจากข้อมูลปัจจุบันใน UC-07 ตาม ASM-03 เพื่อให้การแก้ข้อมูลวงภายหลังไม่เปลี่ยนใบสมัครเดิม

## 4. API / หน้าจอ

| รายการ | Input / Output หลัก | รองรับ |
|---|---|---|
| `GET /events/open` | Output: รายการอีเว้นต์ที่เปิดรับสมัครพร้อมข้อจำกัดของอีเว้นต์ | FR-APP-01, PRE-APP-01 |
| `GET /bands/me/application-profile` | Output: ข้อมูลวงจาก UC-07 และผลตรวจความครบถ้วนแบบอ่านอย่างเดียว | FR-APP-02, FR-APP-05, ASM-02 |
| `POST /applications/validate` | Input: `event_id`, ข้อมูลเพลง/การแสดง; Output: ผลตรวจข้อมูลบังคับและข้อจำกัด | FR-APP-03, FR-APP-05 |
| `POST /applications` | Input: `event_id`, ข้อมูลเพลง/การแสดง; Output: ใบสมัครที่บันทึกแล้วพร้อมสถานะ | FR-APP-04, FR-APP-06 |
| หน้าจอเลือกอีเว้นต์ | แสดงอีเว้นต์ที่เปิดรับสมัครและรับ `event_id` | FR-APP-01, AC-APP-01 |
| หน้าจอกรอกใบสมัคร | แสดงข้อมูลวงแบบแก้ไขไม่ได้ รับข้อมูลเพลง/การแสดง และแสดง validation | FR-APP-02, FR-APP-03, FR-APP-05, AC-APP-04 |
| หน้าจอผลการส่งใบสมัคร | แสดงสถานะ "รอตรวจสอบ" หรือข้อความส่งไม่สำเร็จ | FR-APP-04, FR-APP-06, AC-APP-03, AC-APP-05 |

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| PRE-APP-01 | ตรวจ session ของวงก่อนเรียก `GET /events/open`, `GET /bands/me/application-profile` และ `POST /applications` | ใช้แล้ว |

ข้อกำหนด NFR ยังไม่มีค่าตัวเลขใน spec จึงยังไม่กำหนดรายละเอียดการทดสอบประสิทธิภาพหรือมาตรการความปลอดภัยเพิ่มเติมจนกว่าจะตอบ Q-03

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| AC-APP-01 | `test_AC_APP_01_create_application_for_selected_event` | เตรียมวงที่เข้าสู่ระบบ อีเว้นต์เปิดรับสมัคร และข้อมูลไม่เกินข้อจำกัด ตรวจว่าบันทึกสำเร็จและผูกกับอีเว้นต์ที่เลือก |
| AC-APP-02 | `test_AC_APP_02_store_band_snapshot_and_performance_data` | ส่งใบสมัครสำเร็จ แล้วตรวจว่า snapshot ข้อมูลวงและข้อมูลเพลง/การแสดงถูกเก็บครบในใบสมัคร |
| AC-APP-03 | `test_AC_APP_03_show_pending_review_status` | ตรวจ response และหน้าผลการส่งว่ามีข้อความ "รอตรวจสอบ" ตรงตัว |
| AC-APP-04 | `test_AC_APP_04_reject_incomplete_or_over_limit_application` | ส่งข้อมูลที่ขาดฟิลด์บังคับ หรือเกินข้อจำกัดของอีเว้นต์ ตรวจว่าแจ้งให้แก้ไขและไม่สร้างใบสมัคร |
| AC-APP-05 | `test_AC_APP_05_do_not_create_partial_application_on_save_failure` | จำลองการบันทึกล้มเหลว ตรวจข้อความผิดพลาดและตรวจว่าไม่มีใบสมัครที่ไม่สมบูรณ์ |

ข้อจำกัด: AC-APP-04 ต้องใช้ค่าข้อจำกัดจริงของอีเว้นต์ และ NFR ยังทดสอบเชิงตัวเลขไม่ได้จนกว่าจะตอบ Q-02 และ Q-03

## 7. ลำดับงาน

1. เตรียมการตรวจสิทธิ์วงที่เข้าสู่ระบบและรายการอีเว้นต์ที่เปิดรับสมัคร (PRE-APP-01, FR-APP-01)
2. เชื่อมข้อมูลวงจาก UC-07 และแสดงผลแบบแก้ไขไม่ได้ พร้อมตรวจความครบถ้วนของข้อมูลวง (FR-APP-02, FR-APP-05, ASM-02)
3. สร้างฟอร์มข้อมูลเพลง/การแสดง โดยแยกข้อมูลบังคับและไม่บังคับ (FR-APP-02, ASM-04, ASM-05)
4. สร้าง validation สำหรับข้อมูลบังคับ ความยาวการแสดงรวม และจำนวนเพลงตามอีเว้นต์ (FR-APP-03, FR-APP-05, AC-APP-04)
5. สร้างการบันทึกแบบไม่สร้างใบสมัครบางส่วนเมื่อเกิดข้อผิดพลาด (FR-APP-06, AC-APP-05)
6. บันทึก snapshot ข้อมูลวง ข้อมูลเพลง/การแสดง และสถานะ "รอตรวจสอบ" ในใบสมัคร (FR-APP-04, ASM-03, ASM-06)
7. แสดงผลการส่งสำเร็จ/ไม่สำเร็จและสถานะตามที่กำหนด (FR-APP-04, FR-APP-06, AC-APP-03, AC-APP-05)
8. เขียนและรันการทดสอบตาม AC-APP-01 ถึง AC-APP-05

## 8. สิ่งที่ยังไม่ทำ

- Q-01 วงสามารถสมัครอีเว้นต์เดียวกันซ้ำได้หรือไม่ และถ้าไม่ได้ ระบบต้องจัดการใบสมัครซ้ำอย่างไร? ส่วน validation และการจัดการใบสมัครซ้ำจะยังไม่สร้างจนกว่าจะได้คำตอบ
- Q-02 เวลาแสดงสูงสุดและจำนวนเพลงสูงสุดที่ผู้จัดงานกำหนดมีค่าเป็นเท่าใด และกำหนดแยกตามอีเว้นต์ได้หรือไม่? ส่วนค่าข้อจำกัดและการทดสอบค่าจริงจะยังไม่สร้างจนกว่าจะได้คำตอบ
- Q-03 มาตรการรักษาความปลอดภัยของข้อมูลวง และจำนวนวงที่ต้องรองรับพร้อมกัน/เวลาตอบสนองเป้าหมายคือเท่าใด? ส่วนมาตรการเพิ่มเติมและ performance test จะยังไม่สร้างจนกว่าจะได้คำตอบ
